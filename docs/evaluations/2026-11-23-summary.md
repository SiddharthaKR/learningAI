## Prioritized findings

### P1 - Production build is broken in this environment

`npm.cmd run build` failed twice with `TypeError: Cannot read properties of undefined (reading 'length')` in webpack's `WasmHash._updateWithBuffer`. The outside-sandbox repeat also failed, so the observed failure is not explained by sandbox restrictions. No root cause beyond the failing compilation stage was established; do not attribute it to application logic or prescribe an upgrade/cache deletion without further investigation. The post-build artifact scanner was not reached.

**Next task:** reduce the build failure to its failing module/hash input and inspect the installed Next.js/webpack behavior before choosing a fix. Acceptance: the exact package build command and its artifact scanner complete successfully on the target environment.

### P1 - Mixed PDFs silently omit scanned pages

A synthetic two-page PDF contains native introduction text on page 1 and an image-only code on page 2. `extractPdf` returned only page 1. Calling the existing OCR function directly found text on page 2. The parser returns as soon as any native-text blocks exist, so remaining scanned pages are never OCRed.

**Next task:** specify per-page extraction/OCR decisions and honest partial outcomes, then cover the mixed fixture with a regression. Preserve native text and page numbers.

### P1 - Enabled vision cannot persist its generated chunks

Using the actual indexing service with a controlled mock vision response generated one image chunk with `sourceId = documentId + "-img"`. Snapshot validation rejected it: source IDs must be 64 hexadecimal characters and resolve to the ready document. Normal upload/shared-index entry points also omit vision configuration, which hides this failure in the usual path.

**Next task:** agree configuration precedence and chunk identity/ordering, then test real indexing through validation, publication, reload, search, and deletion. Wiring the existing option alone is insufficient.

### P1 - Current visual-description settings discard useful work

The existing `describeImages` helper produced zero description blocks for both tested full-page images. Page 6 returned HTTP 200 but empty final content; page 19 hit the helper's 30-second timeout. A diagnostic page-6 retry with a 65-second observation window and the same prompt/output limit returned after **34.04 seconds** with `finish_reason: "length"`, **512 completion tokens**, empty `message.content`, and **1,842 characters in `message.reasoning`**. The helper catches the resulting no-content error and silently skips the image.

A simple synthetic image-code question succeeded twice through the same configured vision endpoint, including once with an explicit per-request thinking setting. Thus, these observations establish a failing dense-page description path, not that the configured model cannot process images. They do not establish whether the endpoint honors the thinking flag.

**Next task:** benchmark an approved prompt, reasoning/output budget, timeout, and failure-status policy. Do not treat reasoning text as a verified description. Test dense diagrams and tables against original page evidence.

### P1 - Evidence can be presented with the wrong page citation

`expandNeighbors` merged page-2 text containing a unique fact into a result whose retained citation was page 1. This is a deterministic direct reproduction using real search code. The context has one citation although its text spans pages.

**Next task:** approve passage-level evidence/citation representation and update chunk expansion, open-section/tool outputs, validation, and UI consumers together. Regression: a fact from a neighboring page retains that page as its source.

### P1 - Graph layout blocks other users

The default 300-tick `incrementalLayout` runs synchronously. Module benchmarks with three samples per size took **0.74-1.09 seconds at 1,000 nodes** and **11.59-11.81 seconds at 5,000 nodes**, blocking a zero-delay timer for the same interval.

This was also reproduced through the isolated app: an initially empty synthetic account was seeded with 1,000 propositions and 999 chains. A position commit that triggered settling took **1.35 seconds**. Another user's five overlapping preference requests took **1.02-1.34 seconds**, versus **30-88 milliseconds** in five idle samples. All requests succeeded, but the server paused useful work for another user.

**Next task:** select an execution/scheduling approach that preserves graph semantics and publication consistency while keeping request handling responsive. Regression: repeat the same cross-user experiment and compare against an approved responsiveness budget. The benchmark is not a browser frame-rate measurement.

### P2 - Table splitting loses column context

A synthetic 180-row table passed through the existing table-aware chunker became four chunks. Header presence was `[true, false, false, false]`. Separately, the current PDF parser does not emit structured table blocks, so PDF tables normally enter ordinary text chunking.

**Next task:** agree table extraction and representation, preserve headers/units/notes and complete row meaning in every split, and evaluate continuation/merged-cell layouts. This requires more than increasing chunk size.

### P2 - OCR can alter exact numeric values

The visually checked synthetic image says `SCANNED CODE 73921`; existing OCR returned `SCANNED CODE 73321`. This is one controlled example, not an OCR accuracy rate. It demonstrates why successful OCR and a ready status do not establish exact-value correctness.

**Next task:** include critical numeric values in the gold evaluation and define how uncertain OCR is verified or disclosed before answering.

### P2 - Upload work is duplicated

For explicit personal/shared destinations, the route indexes the bytes to produce attachment text and then calls store upload, which indexes them again. This call path is confirmed in source. The tested 4.36 MB manual took **28.50 seconds** to upload/index through the personal route; direct indexing in a separate process took **13.98 seconds** in the refreshed benchmark. Those timings have different overhead and cache conditions and do not prove an exact 2x speedup is available.

**Next task:** count extraction/OCR/vision invocations per route request, then approve a boundary for reusing one validated result. Preserve duplicate detection, checked ownership, and atomic publication.

### P2 - Lint blocks the architecture gate

Four restricted-import errors occur at `app/api/knowledge/map/route.ts:2`, `app/api/knowledge/map/route.ts:3`, `app/api/knowledge/section/route.ts:2`, and `components/knowledge-map-model.ts:15`. The rule requires the app/server and browser/core barrels. These are verified rule violations, not evidence of a runtime data leak.

**Next task:** route exports/imports through the intended public boundaries and rerun lint, type checking, and affected map/section tests.

## What works, and what the measurements suggest

- Login/logout, incorrect-password rejection, synthetic account language preferences, chat creation, knowledge controls, personal document isolation, shared visibility, invalid uploads, duplicate upload handling, section access, and page HTTP responses passed the sampled checks.
- Three concurrent users received their own expected short response, and cross-user chat reads returned 404. This is a small correctness exercise, not a capacity limit.
- Live disconnect/replay/abort/resend succeeded without duplicating the original input. Practice created a problem and then persisted a `conclude` tool verdict of `solved` for the submitted answer.
- Prepared BM25 search was fast on the synthetic corpus: p95 **0.41 ms / 3.10 ms / 17.62 ms** at **153 / 1,530 / 15,300 chunks**, 30 samples per size in the refreshed run. These are repeated copies of one document and already-prepared ranker data, not a diverse production corpus or end-to-end network latency.
- The five-part PDF answer required three knowledge searches and about **73.2 seconds** from durable input timestamp to final record update. That observation includes provider/tool scheduling and concurrent control work; it does not isolate inference time.
- Do not prioritize embeddings solely because PDF answers have been unreliable. Fix missing/misrepresented evidence and citation attribution first, then measure remaining ranking misses on held-out cases.

## Limits and remaining acceptance work

- The proposed 30-question held-out gold corpus and a multi-document quality gate were not completed. This run used 18 manual retrieval questions, five anchor facts in one live answer, four abstention cases in one live answer, one Japanese answer, and controlled synthetic diagnostics. No model-accuracy percentage beyond those samples is justified.
- HTTP 200 and HTML response size do not establish successful browser hydration, focus behavior, scrolling, keyboard access, rich-content rendering, or visual smoothness.
- Browser automation host was unavailable. Automatic approval review rejected selecting an existing Chrome window because it showed unrelated browsing content and could expose private activity. Approval for a dedicated test window was requested and remains pending; no workaround accessed that window.
- Production-mode latency, deployment/systemd behavior, outbound-traffic observation, restart-under-load recovery, real long-session compaction, and the proposed 30-minute production soak remain unverified. Production acceptance is blocked by the failed build; running a development soak would not close that gate.
- Full graph extraction/auditing, visual-maker/background research jobs, large upload memory peaks, and multi-process mutation/cache behavior need dedicated live scenarios. Existing passing tests cover parts of those systems but are not live acceptance evidence.
- No parser architecture, schema migration, model policy, worker strategy, or rollout/reindexing change was selected or implemented.

## 6A — session flags, history audit, and monotonic sticky persistence

### Smallest concrete seams

1. **Contracts and store port:** extend `src/core/ports.ts:ChatStore` with a narrowly scoped sticky operation (name is a proposal, e.g. `markKnowledgeUsed(id)`) and one operation that saves settings and the associated audit event(s) in a single record write. Existing flag fields in `src/core/contracts/chat.ts` need no duplicate additions. Decide the audit event shape with the human before authoring it.
2. **Store implementation:** implement these in `src/store/chats.ts:createChatStore`. Each mutation must read the latest record, preserve every unrelated field, and synchronously complete its write before returning. The sticky method only ever assigns true, is idempotent, and throws for a missing/unwritable chat. No settings/UI request may write or clear it. `saveMessages`, `saveTree`, usage writes, and settings saves already re-read records and therefore preserve a freshly written sticky flag if the new methods follow the same discipline.
3. **Atomicity:** setting true and exposing chunks must have a strict ordering: retrieve -> check successful nonempty result -> persist true -> return result to the agent. A failed sticky persist must prevent chunks from being returned. No setting at turn settlement: that would allow a web call in the same run to escape approval. A synchronous fresh-record read/write gives process-local no-await ordering. If “atomically” also requires crash-safe file replacement, change the central `writeChat` to same-directory temporary write + rename (and clean up failure), using existing snapshot/account writer patterns. This is a small shared choke-point change, but its broader store effects must be approved. It does not alone give cross-process locking.
4. **Settings route:** modify `app/api/chats/[id]/settings/route.ts:PUTImpl` to use the atomic settings-plus-audit operation. Compare effective booleans (`=== true`) so absence -> false is not a semantic change; do not emit duplicate audit entries for identical PUTs. Preserve current auth, validation, rejection of client model selection, and model-level clamping. After successful persistence, emit the existing owner-scoped `record-changed` event to synchronize open tabs (the store's content-writer silence law points toward route-level emission).
5. **History transport:** a native custom marker is the existing mechanism for durable transcript UI events. If approved, add its custom type and constructor in `src/core/native-messages.ts`, its neutral structured payload in contracts, and project it in `src/core/view.ts:projectMarker`. Store stable keys/booleans/time, not localized prose. Localize only at rendering. Decide whether its canonical model-facing content is needed; if it is UI-only, explicitly drop it in `toLlmMessages`, as is done for plan blocks and dismissal markers. The current fallback converts all other custom messages into user text, even empty content.

### Important concurrency and ordering details

- `src/server/turn-service.ts:persistTurn` reads the latest record and appends `turnMessages.slice(baseCount)` to its current messages. It should preserve a settings audit marker appended during the run. Test that explicitly; do not rewrite using the record captured at turn start.
- Appending an audit marker while a question is unanswered can place a custom message between an assistant tool call and its later result. If model-facing, the adapter may emit an intervening user message and violate the provider's tool-result adjacency requirement. UI-only audit markers avoid that wire issue, but this is a design choice to approve, not infer.
- Write-ahead `saveMessages` uses a merged array prepared after compaction. A settings request cannot interleave with a purely synchronous stretch, but can arrive across awaited compaction. The handler does re-read after `ensureCompacted`; test the chosen snapshot boundary and ensure audit entries are not lost.
- `updatedAt` currently represents conversation activity; `saveSettings` intentionally does not reorder the sidebar. Decide whether an audit history append counts as conversation activity. Keeping settings changes silent for ordering is consistent with current store comments, but remains an explicit decision.

### Focused evidence to add/extend

Extend `tests/settings-body.test.ts`, `tests/settings.test.ts`, `tests/chat-store-events.test.ts`, and `tests/office-chat-isolation.test.ts`; add a focused Task 6 store/session test if the existing suites become too diffuse. Cover absent flags OFF, invalid types, ON/OFF transitions, no-op PUTs, one/both changed controls, isolation, atomic settings/audit failure, sticky idempotence, sticky preservation through all other writers, and marker survival through a settling foreground turn. `tests/support/test-stores.ts` provides isolated scoped stores; `tests/bootstrap.mjs` is required by that support module. Native adapter/view tests should pin whether the marker reaches the model.

## 6B — tool execution, prompt provenance, and composition

### Tool and composition changes

1. **New local tool module:** create a small `src/agent/tools/knowledge.ts` builder. Inject `Retriever`, explicit owner ID, chat ID, and a narrow sticky persistence callback/port. Its TypeBox schema is only `{ queries: string[1..4] }`; do not accept owner, paths, language, snapshots, or session settings as model arguments. Retain the retriever's trim/nonempty validation as a runtime backstop. Use `serverExecute` for existing timeout/result mapping, and inspect its abort signal before the final persist/return boundary. Return structured results with citation fields in `details` and text/JSON model content through the standard mapper.
2. **Registration:** `src/agent/tools.ts:createTeacherTools` and `createProberTools` need an optional injected knowledge context gated by the turn's captured Knowledge flag; `src/agent/tools/practice.ts:PracticeToolContext` / `practiceTools` need the equivalent. An OFF session's registry must omit the name entirely. Do not add this to global `EnabledTools`/`WRITABLE_TOOL_KEYS`: the session flag is its authority. Keep existing `healToolRecord` behavior and test that argument healing does not weaken query cardinality/nonempty validation.
3. **Server composition:** in `src/server/chat-handler.ts:handleChatInput`, capture `currentUserId()` once as an explicit owner and use the session snapshot to create the tool context. Instantiate `new Bm25Retriever(loadKnowledgeChunks)` here or in a small server composition helper, then inject it down; do not import server stores from the agent tool. Pass the same context into prober, teacher, and practice branches. `AgentBuildOptions` may carry explicit owner/session flag data for factory tests, but the authoritative store callback belongs in injected tool context.
4. **Background composition:** `src/server/chat-handler.ts:spawnOfficeJob` already has the explicit owner and checked stores. Extend `JobRunnerDeps` in `src/agent/subagents/runner.ts` with the narrow knowledge context factory/dependency. `runResearchJob` must pass job owner, chat ID, fixed teaching language, and the appropriate captured policy into `ResearcherRunOptions`. `src/agent/subagents/researcher.ts:runResearcherAgent` composes the same knowledge tool builder alongside the allowed web tools. A background chunk must set the originating session's sticky flag before entering the researcher's context, even if the researcher later fails or never delivers its brief.
5. **Research availability:** currently `research` exists only when Web is ON (`researchAvailable(chatId)`), and `runResearcherAgent` always constructs web tools, with Web OFF enforced at execution. If a Knowledge-only researcher is required, change `jobTools`/runner gates so local research can be dispatched with Knowledge ON and Web OFF, and omit all web tools when Web OFF. If only direct foreground knowledge use is intended, avoid expanding dispatch scope without human approval. The spec requires no web tool registration while OFF; execution refusal alone is weaker.

### Prompts and citations

- Put shared knowledge doctrine in one numeric shared fragment (or extend the existing accuracy fragment if approved) with explicit Japanese AND English formulations plus key terms/acronyms, up to four queries. Query language is independent from response language. Do not claim BM25 translates monolingual documents automatically.
- `src/agent/prompt-segments.ts:PRACTICE_SHARED_FRAGMENTS` is an allowlist. A new shared fragment will reach teacher/prober automatically but must be explicitly admitted for practice. Extend `composeInstructions` assertions for all three kinds.
- Add the same query/provenance instruction to the researcher system prompt or compose a shared exported instruction there. The researcher currently has an inline `INSTRUCTIONS` string and only states general source/background separation; it does not load shared prompt fragments.
- Require document-based claims to identify filename and the exact supported locator: PDF page, PPTX slide plus title, DOCX heading/paragraph, or text heading/line range. Keep sourced document claims distinct from uncited general background. Call out ambiguous slides/diagrams and missing evidence without guessing. Treat retrieved text as source data, never executable instructions or authorization for a web fetch.
- Retain `KnowledgeCitation` as the canonical data shape (`src/knowledge/contracts.ts`). No full path or fabricated download/source URL is needed. A text-only inline citation convention, clickable citations, and a search-result citation card are different UX choices; confirm the intended one.

### Next-turn semantics conflict that needs a ruling

The accepted spec says both controls change from the **next agent turn**. Current code contradicts a strict frozen-turn interpretation:

- `researchAvailable` re-reads current stored Web state; job construction occurs later than foreground composition.
- `WebToolPolicy.enabled` in the runner is a live callback, explicitly documented in `src/agent/tools/web.ts` to stop an in-flight researcher when Web is turned off.
- Approval issuance and acceptance in `spawnOfficeJob` also check live Web state.

Do not silently remove this behavior or silently apply it to Knowledge. Establish whether “turn” means an accepted foreground request, a background run, or each researcher LLM step; whether turning Web OFF immediately cancels outbound work; and whether a job dispatched before a toggle snapshots dispatch settings or start settings. Snapshot settings for capability registration once at the approved boundary. Sticky knowledge use should remain a **live monotonic safety input**, since a parallel knowledge call must affect a later outbound call in the same run. Knowledge returning after OFF must follow the approved snapshot semantics rather than ad hoc live checks.

There is also a parallel-call race: a web request may evaluate approval before an overlapping knowledge retrieval marks sticky use. If the run began Knowledge ON, the captured Knowledge flag can require approval even before sticky use, but a live flag turned OFF could erase that protection. This needs a deterministic test with deferred promises, not timing sleeps.

## 6C — localized controls, marker, citation UI, and integration

The existing `components/model-picker.tsx:saveSession` demonstrates full-object PUT behavior, but office builds reject body `model`, so do not blindly forward legacy model fields.
2. **Keep both toggles:** PUT is replace-whole. Each toggle interaction must send the other current flag too (and any other permitted setting), or a Knowledge interaction can silently turn Web OFF. Multiple tabs/stale client saves can still overwrite newer settings under existing API semantics. Whether to use an explicit flags PATCH or keep full replace with serialized UI writes needs approval; do not change the established route contract incidentally.

Adopt the field in `syncFromServer`, and ensure stream settlement / `record-changed` paths actually refresh it. A `markKnowledgeUsed` caller can emit `record-changed` after the successful first transition, or the normal settle sync can refresh it; decide if immediate display during retrieval is required. The server remains the source of truth; do not infer sticky use just from current messages, because context compaction can remove chunks.
4. **Audit rendering:** add a localized rendering case for the projected audit UI part in chat history. Preserve stable neutral payloads so changing UI language changes presentation without rewriting history or session teaching language. Add visible next-turn wording and localized save/loading/error states according to the approved UX.

## Approval blockers and top risks

1. **Policy timing conflict:** strict next-turn semantics conflict with existing immediate Web-off enforcement and late background construction. Human must approve a precise snapshot boundary and in-flight OFF behavior; tests must pin it.
2. **Sticky atomicity and history races:** a successful chunk return before durable sticky write can bypass approval. Direct file writes can tear on crash; client/turn snapshots can erase mid-turn audit entries if new writers avoid fresh-record mutation. Confirm the required atomicity level, keep the setter monotonic, and test persist failure plus deferred parallel calls.
3. **Scope and presentation ambiguity:** Knowledge-only research dispatch, model-visible versus UI-only audit events, citation interaction, control location, and full-replace settings behavior are not fully specified. In particular, model-visible audit markers inserted after pending question calls can break tool-result adjacency. Present these as concrete decisions before implementation under AGENTS.md.

Before code edits, the parent should read the relevant local Next.js guides under `node_modules/next/dist/docs/` for the route/page/component changes. This audit did not write framework code, run verification commands, or claim tests pass.
